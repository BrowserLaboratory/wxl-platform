## 規則完整定義

---

### P-1 — 標點風格（破折號控制）

**定義**：教學文章中，例行性的子句銜接使用逗號（，）或冒號（：）。破折號（`——`）僅限用於戲劇效果（開場 hook、笑點轉折）。

**判定清單**（遇到每個 `——` 時逐條檢查）：

1. `——` 後接因果子句（因為/由於/因此）→ 替換為冒號（：）
2. `——` 後接反問或澄清式問句 → 替換為逗號（，）
3. `——` 引出對前方詞語的定義或解釋 → 替換為冒號（：）
4. `——` 引出對比或轉折，且內容確實令人意外或具幽默效果 → **保留**
5. 以上皆非 → 預設替換為逗號（，）

**判斷流程圖**：

```
這個 —— 的用途是什麼？
  ├─ 後接因果（因為/由於/因此）       → 改用冒號 ：      [#1]
  ├─ 後接反問或澄清問句              → 改用逗號 ，      [#2]
  ├─ 解釋前面的名詞/概念             → 改用冒號 ：      [#3]
  ├─ 製造戲劇效果/驚喜/幽默          → 保留破折號 ——    [#4]
  └─ 以上皆非                        → 預設改用逗號 ，  [#5]
```

**違規/合規對照**：

| 違規 ❌ | 合規 ✅ | 適用判定 |
|---------|---------|---------|
| `答案——但我連鍵盤都不會打` | `答案，但我連鍵盤都不會打` | #5 預設→逗號 |
| `用途——它會讓程式暫停` | `用途：它會讓程式暫停` | #3 解釋→冒號 |
| `大概會崩潰——因為在數學裡` | `大概會崩潰：因為在數學裡` | #1 因果→冒號 |
| `**Flow Control**——讓程式根據條件` | `**Flow Control**：讓程式根據條件` | #3 定義→冒號 |
| `明天就要考試了——結果我打開了遊戲` | 保留 ✅（戲劇轉折） | #4 意外/幽默→保留 |

**例外**：無。

**附加說明**：當移除破折號時，如果原本的破折號兼具「強調」功能（讓讀者注意某個詞），需要用其他方式補回強調效果——最常見的替代方案是對關鍵詞加 **bold**。例如：`computer——拆開來看` → `**computer**，拆開來看`。

**統計門檻**：全文保留的 `——` 數量不應超過全文 `——` 總數的 30%。如果超過，重新審查是否有些被誤判為「戲劇效果」。

### T-1 — 術語前向引用控制

**定義**：不得在正式教學點之前使用技術術語。若必須提及未教的概念，使用白話描述或受控前向引用（立即附帶括號解釋＋預告何時正式教）。

**判斷流程圖**：

```
我要在這裡使用術語 X：
  ├─ X 已經在前面的段落正式教過了嗎？
  │   └─ 是 → 直接使用（合法的向後引用）
  ├─ X 是本段正在教的概念嗎？
  │   └─ 是 → 直接使用（這就是教學點）
  └─ X 還沒教過：
      ├─ 可以用白話描述嗎？ → 用白話替代
      └─ 不可避免必須用正式術語？ → 受控前向引用
          需滿足：(a) 括號給白話解釋
                  (b) 標註「後面會正式介紹」
                  (c) 不深入展開
```

**違規/合規對照**：

| 違規 ❌ | 合規 ✅ |
|---------|---------|
| 1-1 中使用「變數名稱」（變數在 1-2 才教） | 「指令或資料儲存空間的名稱」 |
| 直接說「布林值」但未解釋 | 「一種只有對/錯兩種答案的值——叫做**布林值（Boolean）**（1-3 會正式介紹）」 |

**例外**：無。

**跨節審計要點**：進行跨節審計時，須建立「術語教學點對照表」：

| 術語 | 教學點所在節 | 可出現的範圍 |
|------|------------|------------|
| （依據實際文章內容填寫） | | |

逐節掃描時，若某個術語出現在其「可出現範圍」之前，須改為白話替代或受控前向引用。

### S-1 — 類比元認知橋接

**定義**：每個類比或比喻之前，須有一句後設認知橋——告訴讀者「為什麼要做這個比較」，再進入比較本身。

**判斷流程圖**：

```
我要展開一個類比/比喻：
  ├─ 前一句有解釋「為什麼要用這個比喻」嗎？
  │   └─ 是 → 通過
  └─ 否 → 在類比前加一句 meta-cognitive bridge
      可選橋接模式：
      ├─ 目的宣告：「為什麼要講這個？因為...」
      ├─ 問題引導：「你有沒有想過，X 跟 Y 有什麼關係？」
      └─ 缺口指認：「[前面的東西] 聽起來很抽象。讓我們用一個你絕對遇過的場景...」
```

**違規/合規對照**：

| 違規 ❌ | 合規 ✅ |
|---------|---------|
| `你用過計算機吧？按 1+1 然後按 =` | `為什麼先解釋「電腦就是計算機」呢？那就得問你一個問題：你用過計算機吧？` |
| `想像學校的置物櫃：` | `電腦的記憶體位址長得像 0x7FFF...，沒有人類記得住。所以我們需要一個「翻譯」——想像學校的置物櫃：` |

**例外**：**Hook 段落的開場類比不需要 bridge。** 因為 hook 的功能本身就是吸引注意力，讀者預期開頭會有一個引人入勝的場景。判斷標準：如果類比出現在 H2 段落的第一段（開場），且段落的功能是 hook → 不需要 bridge。其他位置的類比都需要 bridge。

### S-2 — 笑話後語氣恢復

**定義**：笑話元素（顏文字、括號笑話、搞笑離題）之後，下一句須包含明確的回歸連接詞，將敘事拉回主線。

**H3 邊界條件**：當笑話出現在 H3 小節末尾且下一個結構元素是新的 H3 標題時：
- 若新 H3 延續同一主題 → 不需連接詞（標題本身是結構分界）
- 若新 H3 切換到不同子主題 → 新 H3 下第一句須包含簡短過場

**判斷流程圖**：

```
這段文字包含幽默元素（kaomoji / 笑話 / 自嘲）：
  ├─ 下一句是否有語氣恢復連接詞？
  │   └─ 是 → 通過
  └─ 否：
      ├─ 笑話在 H3 末尾，下一個是新 H3？
      │   ├─ 新 H3 延續同主題 → 不需連接詞（通過）
      │   └─ 新 H3 換主題 → 新 H3 下第一句需過場
      └─ 非 H3 邊界 → 必須加連接詞
```

**語氣恢復連接詞清單**：

| 連接詞 | 功能 | 適用場景 |
|--------|------|---------|
| `沒錯！` | Callback 確認——承接笑話前的論點 | 笑話是對前面論點的幽默延伸 |
| `回到正題——` | 明確的軌道切換 | 笑話跟正文主題無直接關聯 |
| `說真的，` | 從玩笑切到認真 | 笑話後要接嚴肅的重要觀念 |
| `不過話說回來，` | 溫和的回歸 | 笑話是短暫的岔題 |
| `好了好了，` | 自覺收斂——「我知道我離題了」 | 笑話比較長，需要明確收回 |
| `總之，` | 簡潔的歸結 | 笑話後直接進入結論 |

**違規/合規對照**：

| 情境 | 違規 ❌ | 合規 ✅ |
|------|---------|---------|
| 連續段落中笑話後 | `（阿飄嚇死了 ╮(╯_╰)╭）電腦做每件事都需要指令` | `（阿飄嚇死了 ╮(╯_╰)╭）沒錯！計算機不會自作主張` |
| H3 邊界+同主題 | — | 不需連接詞（合規） |
| H3 邊界+換主題 | 直接進入新主題無過場 | `接下來我們換個方向，看看...` |

**例外**：見 H3 邊界條件。

### S-3 — 段落過場密度

**定義**：H2 層級的主要概念轉換處，過場段須有 2–4 句：(a) 總結剛學的、(b) 指出缺口、(c) 鋪設下一段的動機。H3 子步驟之間的過場只需 1–2 句。

**密度標準表**：

| 過場層級 | 位置 | 句數 | 必須包含 |
|---------|------|------|---------|
| 主題過場 | H2 → H2 | 2–4 句 | 摘要 + 缺口 + 動機 |
| 子步驟過場 | H3 → H3（同一 H2 內） | 1–2 句 | 銜接句即可 |
| 全篇過場 | 章末 → 下一章預告 | 3–5 句 | 總結 + 預告 + 情緒收束 |

**判斷流程圖**：

```
這裡是兩個 H2 段落的交界：
  ├─ 交界處的過場文字有幾句？
  │   ├─ 0–1 句 → 不足，需要擴展到 2–4 句
  │   ├─ 2–4 句 → 檢查是否覆蓋「摘要 + 缺口 + 動機」
  │   └─ 5+ 句  → 可能過長，考慮精簡
  └─ 過場是否覆蓋三個功能？
      ├─ 缺「摘要」→ 加一句歸結
      ├─ 缺「缺口」→ 加一句指出限制
      └─ 缺「動機」→ 加一句說明為什麼要學下一段
```

**違規/合規對照**：

| 違規 ❌ | 合規 ✅ |
|---------|---------|
| `電腦會說話了。但它還不會聽。`（一句帶過） | `恭喜你！你已經學會讓電腦開口說話了。但是⋯⋯目前它只會自言自語，像個自言自語的機器人。如果我們想讓它「聽懂」我們說什麼，就得教它一個新技能。` |

**例外**：無。

### C-1 — 程式碼對話式前導

**定義**：每個 fenced code block 前必須有至少一句對話式前導，建立「為什麼要看這段程式碼」的脈絡。標題後不可直接接程式碼。

**三種 Lead-in 模式**：

| 模式 | 適用場景 | 範例 |
|------|---------|------|
| **預告模式** | 引入新語法 | 「來看看 Python 怎麼做加法——比你想的還簡單：」 |
| **挑戰模式** | 展示出人意料的結果 | 「你覺得這段程式會印出什麼？先猜猜看：」 |
| **延伸模式** | 在已知基礎上擴展 | 「印一個東西會了。但如果我想同時印名字和成績，怎麼辦？」 |

**判斷流程圖**：

```
這裡有一個 code block：
  ├─ code block 前面（在最近的 H2/H3 標題之後）有至少一句 prose 嗎？
  │   └─ 否 → 必須補上 lead-in
  └─ 有 prose，但內容只是「看以下範例：」之類的空泛引導？
      └─ 是 → 需要加強，使用三種模式之一
```

**違規/合規對照**：

| 違規 ❌ | 合規 ✅ |
|---------|---------|
| `### 第一步：印文字` 後直接 ` ```python ``` ` | `### 第一步：印文字` → `好，我們來用 Python 說第一句話。打開你的編輯器，輸入：` → ` ```python ``` ` |

**例外**：無。

### E-1 — 錯誤預防（即時提醒）

**定義**：常見初學者語法錯誤須在語法首次引入時立即提醒，不得全部推遲到「常見錯誤」段落。「常見錯誤」區塊仍保留——它的角色是整合性複習，而非首次揭露。

**常見觸發場景表**：

| 新語法 | 高頻錯誤 | 應在何處首次警告 |
|--------|---------|----------------|
| 引號 `"` / `'` | 混用（`"Hello'`） | 引號規則首次說明時 |
| `=`（指派） | 跟 `==`（比較）搞混 | `=` 首次出現在教學中時 |
| `input()` | 忘記回傳值永遠是字串 | `input()` 首次教學時 |
| `int()` 轉換 | 輸入非數字導致 crash | `int(input())` 組合技首次教學時 |
| 縮排 | Tab 和 space 混用 | `if` 語法首次教學時 |
| `print()` 多參數 | 忘記逗號後的空格是自動加的 | `print("A", "B")` 教學時 |

**判斷流程圖**：

```
我正在教一個新語法/新概念：
  ├─ 這個語法有已知的高頻初學者錯誤嗎？
  │   └─ 是 → 在同一個 H3 區塊內加 ⚠️ 或 [!WARNING] 警告
  └─ 否 → 不需要（但仍可在「常見錯誤」區塊統一整理）
```

**違規/合規對照**：

| 違規 ❌ | 合規 ✅ |
|---------|---------|
| 教完 `print("Hello")` 後完全不提引號混用 | 教完後立即加 `> [!WARNING]` 說明 `"Hello'` 會出錯 |

**例外**：若該語法在目前上下文中不會觸發該錯誤（例如只用單引號的段落不需提雙引號混用），可省略。

### M-1 — 心智模型顯式化

**定義**：當程式碼範例隱含展示了一個基礎評估概念（如由內而外求值），教學文章須以逐步追蹤的方式讓概念顯式化。後續章節遇到相同模式時，用 callback reference 連結回最初的顯式化。

**Step-by-step trace 格式**：

```
讓我們追蹤 Python 在背後做了什麼：

1. Python 看到 `print(...)`，知道要「印東西」
2. 但括號裡是 `1 + 1`——Python 先算出 `1 + 1 = 2`
3. 現在變成 `print(2)`——Python 把 `2` 印到螢幕上

記住這個「由內而外」的規則——下一節的 `int(input())` 也是同一個道理。
```

**Callback reference 格式**：

```
還記得 print(1+1) 的「由內而外」規則嗎？int(input()) 也是一樣——
Python 先執行 input()，拿到一個字串，再用 int() 把字串轉成整數。
```

**需要顯式化的常見隱含概念**：

| 隱含概念 | 首次出現 | 後續出現（需 callback） |
|---------|---------|---------------------|
| 由內而外求值 | `print(1+1)` | `int(input())`、`print("Hello, " + name)`、複合布林表達式 |
| 字串串接 vs 數學加法 | `"1" + "2" = "12"` | 任何涉及 `+` 的上下文 |
| 條件的短路求值 | `and` / `or` | 複合條件判斷 |
| 變數覆寫（非數學等號） | `x = 5; x = 10` | 計數器 `i = i + 1` |

**判斷流程圖**：

```
這個 code block 教了一個新語法：
  ├─ 隱含了一個「可遷移到其他場景」的底層概念嗎？
  │   ├─ 是 → 需要 step-by-step trace 顯式化
  │   └─ 否 → 不需要
  └─ 使用了一個「前面已經顯式化過」的底層概念嗎？
      ├─ 是 → 需要 callback reference
      └─ 否 → 不需要
```

**違規/合規對照**：

| 違規 ❌ | 合規 ✅ |
|---------|---------|
| `電腦會先算出 1+1 的結果，再把答案印出來`（一句帶過） | `Step 1: Python 看到 1+1，計算得到 2` → `Step 2: Python 看到 print(2)，把 "2" 印出來` |

**例外**：純粹的語法示範（沒有嵌套/複合邏輯）不需要 trace。

### O-1 — 開場動機建立

**定義**：每個教學系列的第一篇文章開頭，須先回答「為什麼要學這個主題？」——以講師的個人故事或讀者可共感的真實情境建立動機，在任何技術概念之前。

**判斷流程圖**：

```
這是系列/書籍的第一篇文章嗎？
  ├─ 否 → O-1 不適用
  └─ 是：
      ├─ H1 標題後、技術概念前，是否包含動機建立段落？
      │   └─ 是 → 通過
      └─ 否 → 需要在技術內容前加入動機段落
          動機段落應包含：
          ├─ 個人故事 或 讀者可共感情境
          └─ 正向回報描述（學了之後能做什麼）
```

**違規/合規對照**：

| 違規 ❌ | 合規 ✅ |
|---------|---------|
| 開頭直接進入技術定義或術語 | 先用個人故事或讀者情境回答「為什麼要學這個？」，再進入技術內容 |

**例外**：系列中非首篇的文章不適用本規則。

**範例**（Python 教學領域，僅供參考，非規則定義）：「我國中的時候，因為零用錢不夠，學了程式之後竟然能靠寫小工具賺到第一筆收入——那一刻我覺得整個世界都不一樣了。」

### W-1 — 程式碼與解說一致性

**定義**：每個附有逐行解讀的程式碼區塊，解讀內容與程式碼須完全對應。解讀不得描述與程式碼不同的語法或操作。

**判斷流程圖**：

```
這個 code block 有逐行解讀嗎？
  ├─ 否 → W-1 不適用
  └─ 是：
      ├─ 解讀中提及的每一行是否在 code block 中逐字出現？
      │   └─ 否 → 修正解讀或 code block 使兩者一致
      ├─ code block 執行後是否產生解讀中描述的預期輸出？
      │   └─ 否 → 修正預期輸出描述
      └─ 解讀是否描述了 code block 中不存在的操作？
          └─ 是 → 移除多餘的解讀或補上對應的程式碼
```

**違規/合規對照**：

| 違規 ❌ | 合規 ✅ |
|---------|---------|
| 解讀說「使用 `len()` 計算長度」但 code block 中沒有 `len()` | 移除該解讀或在 code block 中加入 `len()` |
| code block 印出 `Hello World` 但解讀說「會印出 Hello」 | 修正解讀為「會印出 Hello World」 |

**例外**：偽碼（pseudocode）區塊的解讀允許與實際語法有差異，但須標明為偽碼。

### F-1 — 圖片佔位符雙行格式

> **條件規則** — `format: markdown`（僅當輸出格式為 Markdown 時啟用）

**定義**：每個圖片佔位符須使用雙行格式：

1. 圖片連結行：`![📷 **圖 N**：描述（AI 製圖）]([project-image-path]/figNN.png)`
2. 圖說行：`> 📷 **圖 N**：描述（AI 製圖）`

圖檔尚未產生時，圖片連結行仍須存在（使用預定檔名）。不得使用只有 `> 📷 ...` 而無前導 `![](...)` 的單行格式。

**判斷流程圖**：

```
找到一個 > 📷 圖說行：
  ├─ 前一個非空行是否以 ![ 開頭？
  │   └─ 是 → 通過
  └─ 否 → 需要在圖說行前加入圖片連結行
```

**違規/合規對照**：

| 違規 ❌ | 合規 ✅ |
|---------|---------|
| `> 📷 **圖 3**：變數置物櫃示意圖（AI 製圖）`（單行） | `![📷 **圖 3**：變數置物櫃示意圖（AI 製圖）]([project-image-path]/fig03.png)` + 換行 + `> 📷 **圖 3**：變數置物櫃示意圖（AI 製圖）` |

**例外**：非 Markdown 輸出格式不適用（DOCX 使用表格格式，見 SKILL.md §9.5）。

### V-1 — VitePress container 語法

> **條件規則** — `platform: vitepress`（僅當目標發布平台為 VitePress 時啟用）

**定義**：所有 VitePress custom container 須使用 `> [!TYPE]` 語法（TYPE 為 NOTE/TIP/WARNING/DANGER/DETAILS）。`!` 為必要字元，`> [TYPE]` 寫法不會正確渲染。

**判斷流程圖**：

```
找到一個 > [TYPE] 行（TYPE 為 NOTE/TIP/WARNING/DANGER/DETAILS）：
  ├─ TYPE 前有 ! 嗎？（即 > [!TYPE]）
  │   └─ 是 → 通過
  └─ 否 → 加上 !，改為 > [!TYPE]
```

**違規/合規對照**：

| 違規 ❌ | 合規 ✅ |
|---------|---------|
| `> [WARNING] 想想英文文法` | `> [!WARNING] 想想英文文法` |
| `> [TIP] 小秘訣` | `> [!TIP] 小秘訣` |

**例外**：非 VitePress 平台不適用。其他平台的 callout/admonition 語法請依該平台規範。

### T-2 — 無殘留 TBD 標記

**定義**：已發布的教學文章中不得殘留 `<!-- [START] TBD ... -->` / `<!-- [END] TBD -->` 註解對或獨立的 `<!-- TBD ... -->` 註解。所有佔位標記須已解決並移除。

**判斷流程圖**：

```
掃描全文中的 HTML 註解：
  ├─ 包含 "TBD" 關鍵字（不分大小寫）？
  │   └─ 是 → 違規——須解決內容並移除標記
  └─ 否 → 通過
```

**違規/合規對照**：

| 違規 ❌ | 合規 ✅ |
|---------|---------|
| `<!-- TBD: 補上布林值的例子 -->` | （移除標記，補上實際內容） |
| `<!-- [START] TBD: 待填寫 -->...<!-- [END] TBD -->` | （解決內容，移除標記對） |

**例外**：草稿階段的文件允許 TBD 標記，但發布前須全部清除。

### T-3 — 無空白 UI 元素

**定義**：已發布的教學文章中，不得出現標題存在但內容為空的 custom container（NOTE/TIP/WARNING/DANGER/DETAILS）。內容未準備好時，整個 container 區塊須以 HTML 註解包裹（`<!-- DEFERRED: 描述 -->`）。

**判斷流程圖**：

```
找到一個 > [!TYPE] container：
  ├─ container 內有至少一句實質內容嗎？
  │   └─ 是 → 通過
  └─ 否（只有空行或只有 > 符號）→ 違規
      修正方式：
      ├─ 填入內容
      └─ 或用 <!-- DEFERRED: 描述 --> 替代整個 container
```

**違規/合規對照**：

| 違規 ❌ | 合規 ✅ |
|---------|---------|
| `> [!WARNING] 想想英文文法` + 空白內容 | `<!-- DEFERRED: 引號混用的英文文法類比警告 -->` |
| 可見 container 但內容只有空行 | container 內至少一句實質內容 |

**例外**：無。

### K-1 — 顏文字語氣密度

**定義**：每個教學章節須維持均衡的情感標點密度。計算單位為連續散文行（排除 fenced code block、表格、圖片佔位符）。

- **下限**：每 30 行散文至少 1 個情感標點元素
- **上限**：每 10 行散文不超過 1 個情感標點元素

**與 SKILL.md §3 的關係**：§3 的「1–2 kaomoji per paragraph max」是快速參考指引（以段落為單位）。K-1 是精確標準（以散文行數為單位）。當兩者判定結果不同時，以 K-1 為準。

**情感標點元素偵測規格**（三層定義）：

**Tier 1 — 確定性偵測**（regex）：
顏文字——包含以下特徵 Unicode 字元的組合：`╮╯╰╭`、`ʅʃ`、`Σ`、`ω`、`д`、`◕`、`ヮ`、`ﾉ`、`ﾟ`、`✧`、`┌┛`、`ΩДΩ`、`_〆` 等。典型結構：括號內含特殊表情字元，例如 `(ﾉ◕ヮ◕)ﾉ*:･ﾟ✧`、`╮(╯_╰)╭`、`_(´ཀ`」 ∠)_`。

**Tier 2 — 高信度 Heuristic**：
- 全形括號 `（...）` 內含 Tier 1 顏文字
- 全形括號 `（...）` 長度超過 10 字元且包含語氣詞（啊、啦、吧、嗎、呢、哈）
- Type A-D 對話標記：`「...？」` 格式的學生問句，或 emoji prefix（🧑、👨）開頭的對話行

**Tier 3 — 需 LLM 判斷**：
- 全形括號 `（...）` 內容不含顏文字，語氣不確定是否為幽默
- 引述 `「...」` 但不確定是學生對話還是正式引用

**判斷流程圖**：

```
計算一段散文的情感標點密度：
  1. 排除 fenced code block（```...```）
  2. 排除表格行（以 | 開頭）
  3. 排除圖片佔位符行（![ 或 > 📷）
  4. 計算剩餘的散文行數 = L
  5. 計數情感標點元素（Tier 1 + Tier 2）= E
  6. 密度 = E / L
     ├─ 密度 < 1/30 → 太稀疏，需增加
     ├─ 1/30 ≤ 密度 ≤ 1/10 → 合格
     └─ 密度 > 1/10 → 太密集，需減少
```

**違規/合規對照**：

| 違規 ❌ | 合規 ✅ |
|---------|---------|
| 40 行散文完全沒有顏文字或對話 | 第 15 行加入學生對話「老師，這太難了吧？」 |
| 連續 8 行中出現 3 個顏文字 | 顏文字間隔至少 10 行 |

**例外**：無。

## 交叉驗證規則

以下 4 組跨規則檢查在 EAL+ 每輪掃描後執行，防止修正一條規則時違反另一條。

### XV-1：S-2 + C-1 不衝突

**情境**：一個笑話緊接著一個 code block。
**檢查**：S-2（笑話後連接詞）和 C-1（code block 前導）須同時滿足，但不重複且不矛盾。
**解法**：可合併為一句——例如「沒錯！來看看 Python 怎麼處理這個——」同時滿足 S-2 的回歸和 C-1 的 lead-in。

### XV-2：T-1 + M-1 不矛盾

**情境**：M-1 的 callback reference 提及前面章節的術語。
**檢查**：確認 callback 中提到的術語在 callback 出現的位置已經過了教學點（T-1）。
**解法**：如果術語尚未教過，callback reference 中須使用白話描述而非正式術語。

### XV-3：S-3 + S-1 不臃腫

**情境**：一個 H2 過場（S-3）同時需要引入類比（需要 S-1 bridge）。
**檢查**：合併後的過場總長度不超過 5 句。
**解法**：如果超過，將類比移到下一段的開頭，讓過場段保持精簡。

### XV-4：E-1 + C-1 警告位置

**情境**：一個 code block 的 lead-in（C-1）已經暗示了可能的錯誤。
**檢查**：E-1 的 `⚠️` 警告應出現在 code block **之後**（而非重複出現在 lead-in 中）。
**解法**：lead-in 中的暗示保持為自然的對話語氣（「你可能會想用 = 來比較…」），正式的 `[!WARNING]` 放在 code block 後面。

## EAL+ 統一驗證框架

EAL+（Editorial Audit Loop Plus）是一個迭代驗證流程，系統性檢查教學內容是否符合全部 15 條編輯規則。

### 完整 Pipeline

```
[Pre-flight] SKILL.md §11 的 5 問 self-check（快速預檢）
     ↓
[Round N] 固定順序掃描 15 條規則
     ↓
[Post-scan] 4 組交叉驗證（XV-1~XV-4）
     ↓
[Fix] 修正所有 violations
     ↓
[Loop] violations > 0 且 round < 3？→ 回到 Round N+1
     ↓
[Exit] violations = 0 或 round = 3
     ↓
[Final] 模擬讀者校讀
     ↓
[Report] Summary Report
```

### 掃描順序與分組理由

每輪按以下固定順序掃描：

```
P-1 → T-1 → S-1 → S-2 → S-3 → C-1 → E-1 → M-1 → F-1 → V-1 → T-3 → K-1 → O-1 → W-1 → T-2
```

| 分組 | 規則 | 理由 |
|------|------|------|
| 標點/術語（基調） | P-1, T-1 | 影響全文基調的結構性規則，優先處理 |
| 鷹架（連貫性） | S-1, S-2, S-3 | 影響敘事連貫性，在基調穩定後處理 |
| 程式碼/錯誤預防（正確性） | C-1, E-1, M-1 | 影響教學內容正確性 |
| 格式（一致性） | F-1, V-1, T-3 | 影響呈現一致性，在內容穩定後處理 |
| 密度（節奏） | K-1 | 需在其他修正完成後評估（因為修正可能增刪行數） |
| 全域檢查（整體性） | O-1, W-1, T-2 | 整體性驗證，最後執行 |

### Violation Log 格式

每筆違規記錄包含以下欄位：

| 欄位 | 說明 | 範例 |
|------|------|------|
| file | 檔案路徑 | `docs/tutor/py/ch1/1-2.md` |
| line | 行號或行號範圍 | `42` 或 `42-45` |
| rule | 規則 ID | `P-1` |
| desc | 違規描述 | `破折號用於解釋子句` |
| fix | 具體建議修正 | `替換 "——它會" 為 "：它會"` |

**JSON 相容格式**（供 validator 腳本使用）：

```json
{
  "file": "docs/tutor/py/ch1/1-2.md",
  "line": 42,
  "line_end": null,
  "rule": "P-1",
  "desc": "破折號用於解釋子句（判定 #3）",
  "fix": "替換 '——它會' 為 '：它會'"
}
```

### 迭代與終止條件

- **提前終止**：某輪掃描（含交叉驗證）完成後違規數為 0 → 立即終止
- **最大輪次**：完成 3 輪後無論是否仍有違規 → 強制終止
- **全文重掃**：每輪從頭重新掃描（非只檢查修改處），因為修正一個違規可能引入新的違規或連鎖解決其他問題

### 模擬讀者校讀

EAL 通過後（violations = 0 或 3 輪完成），以目標讀者視角從頭到尾讀一遍文章，注意以下感受：

1. **有沒有任何地方讓我停下來想「這是什麼意思？」** → 可能是 T-1 違規或 M-1 缺失
2. **有沒有任何地方讓我覺得「突然跳到另一個話題」** → 可能是 S-3 過場不足或 S-1 bridge 缺失
3. **有沒有任何地方讓我覺得「看到程式碼就很恐懼」** → 可能是 C-1 lead-in 缺失
4. **有沒有任何地方讓我覺得「老師剛才在開玩笑還是認真的？」** → 可能是 S-2 語氣恢復不足
5. **有沒有任何地方讓我讀起來一頓一頓的？** → 可能是 P-1 破折號過多

將所有「不舒服的感受」記錄下來，對照 15 條規則找到根因並修正。

### Summary Report 格式

```
EAL+ Summary Report
====================
Target:  <目標目錄或檔案>
Rules:   P-1, T-1, S-1, S-2, S-3, C-1, E-1, M-1, F-1, V-1, T-3, K-1, O-1, W-1, T-2

Round 1: 23 violations found → 23 fixed
Round 2: 5 violations found → 5 fixed
Round 3: 0 violations found → CLEAN PASS

Reader Simulation: No unresolved issues

Result: PASS (3 rounds, clean on round 3)
```

### 可參數化應用

- **目標目錄/檔案**：可指定任意 markdown 檔案或目錄
- **規則子集**：可指定子集（如僅 P-1 和 C-1）做焦點審計
- **條件規則**：依據目標平台/格式啟用或停用 F-1、V-1
- **工作流程邏輯不變**：掃描順序、violation log 格式、終止條件皆通用

## 規則演化指南

### 從人工修改中辨識規則模式

當教學內容經過人工編輯後，依以下流程辨識潛在規則：

1. **收集修改**：比對編輯前後的 diff，逐項分類修改類型（標點、術語、鷹架、格式⋯）
2. **辨識重複模式**：若同類修改出現 3 次以上，且修改邏輯一致，即為規則候選
3. **撰寫規則假說**：以規則定義格式撰寫草案，附帶 2–3 個判定範例
4. **逆向檢驗**：將規則套用到已完成的「好」段落，確認不會產生誤判

### 正式化門檻

滿足以下全部條件時，規則可正式加入本文件：

- **至少 3 個獨立實例**：同一模式在不同檔案或段落中出現 3 次以上
- **無灰色地帶**：規則的「是/否」判定不需要主觀判斷，或已透過判定清單消除灰色地帶（如 P-1 的 5 條判定清單）
- **有明確的違規/合規對照**：可以寫出具體的「❌ 違規」和「✅ 合規」範例

### 測試新規則（4 類測試）

1. **正向測試**：對已知違規的段落套用規則，確認全部被正確標記
2. **反向測試**：對已通過人工審核的「好」段落套用規則，確認零誤判
3. **邊界測試**：構造刻意模糊的案例，確認規則的判定清單能覆蓋
4. **交叉影響測試**：修正規則 A 的違規後，確認不會違反規則 B（這正是 EAL 多輪掃描的存在意義）

若反向測試產生誤判，有兩個處理方向：
- **收窄規則範圍**：加入豁免條件或邊界定義（如 S-2 的 H3 邊界條件）
- **增加判定清單**：將灰色地帶轉化為具體的 if-then 判定（如 P-1 的 5 條判定清單）
