## The four axes

1. **Completeness.** Does `traceability.md` have holes? Every `{type × field × boundary}`
   combination that the spec's rules can produce must reach an acceptance criterion. Look for inputs,
   repository states (fresh copy, fork, clone, upstream, half-applied), hosts, locales, operating
   systems, tool versions and re-run orderings that the matrix omits, and for matrix rows whose
   expected behaviour disagrees with the spec's rules.
2. **Verifiability.** Can each acceptance criterion be judged pass or fail without interpretation?
   Words like "appropriately", "reasonably", "as needed", "where possible" make a criterion
   unjudgeable: grade those P0. Check that each criterion can be observed at the seam the spec names,
   and that each stage 8 criterion names a surface that can actually be exercised.
3. **Contract conflict.** Does the spec contradict `GLOSSARY.md` vocabulary, an ADR, the Charter or a
   hard rule in `AGENTS.md`, an established seam, an existing test's stated contract, the README's
   documented fork path, or an existing code comment's stated rule? Name the conflicting document and
   line. Overriding is allowed only when the spec says so explicitly.
4. **Red team.** Once this spec is built, what behaviour or attack surface exists that the spec did
   not intend? Check every trust boundary in the spec's table against an attacker on the other side
   of it, every write the setup module makes against the edit-target whitelist, every input against
   every file it lands in, and every guarantee (idempotence, refusal, cleanup on failure) against the
   orderings that could break it. Distinguish intended consequences from accidental ones.
