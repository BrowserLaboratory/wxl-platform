Epic 0009 收尾報告：npm trusted publishing

2026-11-14 · main = df0e042 · 範圍：T-0069～T-0073，以及收尾的串連分析

create-wxl 已經改由 CI 透過 npm trusted publishing 發布，第一個版本 3.1.1 經上游 2FA 核准後上架，帶有指回上游 tag 與 commit 的 provenance。spec 0009 的 AC-1～AC-8 都由對應的票達成，五張票都是 done。

收尾的串連分析找到三條跨越信任邊界的串連（兩條 medium、一條 low～medium），3.1.1 本身沒有受影響。依 review.md，已開 T-0074、T-0075 兩張票（使用者選擇依根因拆開），兩張都還沒排程。另外，分析期間發現 agent 的 shell 讀得到使用者仍有效的 npm session，已請使用者登出。

第一次發布的經過

  1. 使用者完成 MN7（兩條 v* tag ruleset，都 active）、MN2（environment npm，只有一條 v* tag 規則）、MN1（trusted publisher 六欄、撤銷 token），agent 以唯讀 API 核對 MN7、MN2。
  2. #90 合併後，使用者自己讀出 40 碼 SHA 並確認 tag 名稱；agent 確認 SHA 在 main 上、兩份 manifest 都是 3.1.1、遠端沒有同名 tag，才建立 annotated tag 並單獨推送 v3.1.1。
  3. publish-npm.yml 的祖先檢查與閘門通過，npm stage publish 成功並簽出 provenance；這時 npm 的 latest 仍是 3.1.0。
  4. 使用者以 2FA 核准；agent 第一次讀取時 registry 還沒更新，依 RP6 五分鐘後重查已更新（registry 的 modified 是 13:36:45Z），RP6 的版本、provenance 內容與 npm create wxl@latest 三項都通過；使用者完成 MN3。

收尾的串連分析

三關、九位唯讀的子代理：兩位找候選、六位反駁、一位做完整性檢查；parent 另外實測了 git 與 GitHub 的關鍵行為。全文在 review/chain-analysis.md。

#串連嚴重度處置
S-1GitHub 頁面只顯示 7 碼，RP5 (c) 只要求比一欄，前綴相同的惡意 commit 能通過比對；在 terminal 讀 SHA 時，被入侵的 agent 能改共用 checkout 的 refmediumT-0074
S-2origin/main 與 7 碼 SHA 能被同名 ref 遮蔽：一般的 git fetch 會抓到它，使用者、agent 與 CI 的祖先檢查都會指向非 main 的 commitmediumT-0074
S-3agent 與使用者是同一個 macOS 帳號，沒有 agent 用不到的 shell；MN1 之後 agent 的 shell 讀得到有效的 npm sessionlow～mediumT-0075
R-3spec 把 agent 列為對手，又把 admin 排除在威脅模型外，但 agent 實際持有 adminspec 矛盾T-0075，待使用者裁決

其餘候選（staged entry 未綁定 run、永久 tag 成為升級 base、job 內的程式改 bytes、fork 冒名）已被反駁，或只留下 hardening，列在回顧裡。

代價與保留

  • AC-7 帶著兩個缺口結案。RP5 的分頁欄位使用者只回報「都正確」，沒有列出看到哪些欄位，所以 S8-02 要求的欄位清單與 OQ-027 都沒有答案；MN3 的實際選項文字與文件不同。兩者都寫進 T-0073，也讓 S-1 的風險在下一次發布前不會降低。
  • 第一次發布時，RP5 (b) 的 run commit 比對是 agent 做的，使用者只回報核准結果。D13 要的獨立性這次沒有被用到。
  • 這個 epic 的 control 都在 repository 之外（MN1–MN7、RP5）。它們的正確性靠使用者回報與唯讀核對，沒有測試會在設定被改掉時失敗。
  • T-0074、T-0075 需要 spec 0009 revision 3.2，代表要再走一次第 2～9 階段，而且下一次發布前做完才有意義。
