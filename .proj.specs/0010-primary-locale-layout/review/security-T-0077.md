## 成立的發現

### SR-1：P = zh-TW 的舊位址規則 `/zh-TW/*  /:splat` 可能在 Cloudflare 邊緣造成 open redirect（`//evil.com`、`/\evil.com`）（原候選 C3-01）

- 位置：`scripts/generate-redirects.ts:87`；`platform/public/_redirects:67`
- 嚴重度：MEDIUM；類別：Open redirect；驗證者的信心：0.6（讀程式碼推論時給的數字，早於下面的本機實測）
- 本分支引入：是
- 攻擊者的前提：只需要能把一個 URL 交給學生（訊息、講義、討論區）。上游預設 P = zh-TW（.vitepress/locales.ts:9，repo 根目錄沒有 range.json），所以這條規則已經寫進 commit 的 platform/public/_redirects:67，部署到 Cloudflare Pages 後就會生效；每個以繁中為主語系的 fork 也一樣。
- 資料流：攻擊者送出 https://<range>/zh-TW//evil.example/x（或 /zh-TW/%5Cevil.example、/zh-TW/%2F%2Fevil.example 之類的變體）→ 前面沒有任何 /zh-TW/c/ 規則吻合 → 被 `/zh-TW/*` 接住，splat = `/evil.example/x` → 目標 `/:splat` 代換成 `//evil.example/x` → 302 Location: //evil.example/x → 瀏覽器把它當成協定相對 URL，導向外部網域。
- 影響：課程網域變成任意外部網站的跳板，可用於釣魚，例如「從老師的靶場連到假的登入頁」。學生信任 wxl.browserlab.online 或老師自己的網域，這類攻擊特別有效。

**驗證者的判定（讀程式碼推論）**

【判定：成立。以下全部是讀程式碼推論出來的，沒有實際重現，也沒有打過 Cloudflare 或 pages:dev】

一、這條規則是本 branch 新加的。generateFor 只在 primary === 'zh-TW' 時附加 OLD_ADDRESS_RULE `['/zh-TW/*', '/:splat']`，見 scripts/generate-redirects.ts:87、:333-338。上游沒有 range.json（repo 根目錄 Glob 找不到），所以 P 沿用 DEFAULT_PRIMARY_LOCALE = 'zh-TW'（.vitepress/locales.ts:9）。結果是 commit 的 platform/public/_redirects:67 已經寫進 `/zh-TW/*  /:splat  302`。main 原本是 P = en，沒有任何 splat 規則，所以這個入口是本 branch 打開的。

二、攻擊路徑（推論）：
1. 攻擊者送給學生 `https://<range>/zh-TW//evil.example/x`。瀏覽器不會合併路徑裡的 `//`。如果送的是 raw `\`，WHATWG parser 在 https 下也會先把它轉成 `/`。
2. 前面的 `/zh-TW/c/NNN`、`/zh-TW/c/:slug` 都對不上，於是由 `/zh-TW/*` 接住，splat = `/evil.example/x`。
3. 目標 `/:splat` 代換成 `//evil.example/x`，這是協定相對 URL。
4. 我記得 Cloudflare Pages 共用的 asset-server（workers-sdk pages-shared）是這樣處理 _redirects 的：用 `new URL(request.url).pathname` 比對（不解碼、不合併斜線），再用 `new URL(to, request.url)` 解析目標；跨來源時直接輸出絕對的 `destination.href`。這段是憑記憶，沒有在這個 repo 裡驗證。如果記得沒錯，Location 會是 `https://evil.example/x`，也就是 open redirect。
5. 唯一可能擋住的是 Cloudflare 邊緣在交給 Pages 之前先合併 `//`。這正是 spec 自己說還沒驗證的部分（spec.en.md:405 TB5；traceability.md:177 D118）。

三、變體逐一看過：
- `/zh-TW///host`：splat 開頭是 `//`，解析後一樣離站，可以利用。
- `%2F%2F`、`%5C`、`%09`、`%0A`、`%0D`：pathname 不會被解碼，Location 是 `/%2F%2F…` 這類同源路徑，依推論安全。raw tab、CR、LF 會在瀏覽器送出前就被剝掉。
- 所以真正的攻擊向量只有字面上的 `//`（含 raw `\` 轉成的 `//`）。原候選列的 `%5C`、`%2F%2F` 變體依推論不成立，但這不影響主路徑。

四、規則本身的問題不靠 Cloudflare 行為決定：目標第一個字元就是請求文字，同源與否完全看外部平台正不正規化。D118 自己也寫明這條規則「unless Cloudflare normalises the path」才安全，並且有依構造就安全的替代形式。spec 也要求這張 ticket 的 stage 7 審視它（traceability.md:177）。

五、排除條款與 ADR-0005：
- 這是平台的 _redirects，不是某個 challenge 教學用的漏洞，所以依 ADR-0005 屬於缺陷。
- 方法論的 precedent 5 說 open redirect 要「extremely high confidence」才回報（upstream-security-review.md:163）。我的信心只有 0.6，原因是邊緣正規化沒有實測，所以嚴格說未達那個門檻。
- 不過專案 spec 明確把它列為 stage 7 要看、stage 8 唯一擋關的項目（AC-58、S61、D118）。我判定成立，也把不確定性如實寫出。

六、嚴重度給 MEDIUM：課程網域（wxl.browserlab.online 或老師自己的網域）會變成釣魚跳板，學生信任這個網域，而且只要送一個 URL 就能觸發，不需要任何權限。目前的緩解：這條規則還沒合併到 main，正式站上還沒有它；S61 會在 stage 8 的 preview 上擋關。

**建議的修法**

一、優先做法：直接採用 D118 依構造就安全的形式，不靠 S61 觀察結果背書。也就是每個主語系頂層目錄各寫一條 `/zh-TW/<entry>/*  /<entry>/:splat`，每個頂層頁面各寫一條靜態規則，再加 `/zh-TW/  /`。這樣目標第一個段落永遠是固定字面值，請求文字不可能成為 Location 的開頭。依 D118，改規則前要先由使用者選擇。

二、合併前可以先在本機跑 `pnpm pages:dev`（wrangler 用同一套 Pages runtime）：
- 用 `curl -sI --path-as-is` 打 `/zh-TW//evil.example/x`、`/zh-TW///evil.example`、raw `/zh-TW/\evil.example`
- 確認 `new URL(location, origin).origin === origin`
- 再到 stage 8 的 preview 跑完整的 S61

三、如果保留 `/:splat`，S61 通過後也要記錄 Cloudflare 的行為與日期，並開 open question，在 Cloudflare 調整重新導向處理時重測（B88）。

四、考慮只在曾經提供 `/zh-TW/…` 位址的 range 產生這條規則，縮小暴露面（spec.en.md:405 已經指出新建的繁中主語系 range 也會帶這條規則）。

1. **依構造就安全的形式（D118 的替代規則集）**：主語系資料夾的每個頂層目錄各一條 `/zh-TW/<entry>/*  /<entry>/:splat`，每個頂層頁面各一條靜態規則，加上 `/zh-TW/  /`。

parent 的建議是 1：它是 spec 預先寫好的替代形式，保留邊緣的 302，也不依賴 Cloudflare 會不會正規化路徑。
